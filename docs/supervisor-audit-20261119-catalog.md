## Additive public contract for Billing

Keep `GET /api/v1/billing-context` and `core.getBillingContext` compatible; do not silently truncate existing bulk arrays. New Billing consumers use these additive endpoints:

- `GET /api/v1/billing-bootstrap?companyId=aaaaaaaa&financialYearId=bbbbbbbb&currencyCodes=INR,USD`. Optional validated company/year IDs; currencyCodes is an explicit caller selection of at most10 unique uppercase three-letter currency names. Omitted codes request no currency rows. Core does not hardcode Billing's supported currencies. Result `{organisation,company,financialYear,currencies,requestedCurrencyCodes}`; currencies contains only active, non-deleted records matching those requested names, at most10 lightweight `{public_id,name,symbol,active}` DTOs. Missing names are not invented; Billing decides whether its supported/default currency setup is sufficient. Requires default-company, company, financial-year and currency read permissions. All bootstrap DTOs are lean: company `{public_id,name,active}`, financialYear `{public_id,name,startDate,endDate,active}`, organisation `{defaults:{public_id,name,companyId,financialYearId,active},company,financialYear}`. No party contacts/addresses/audit arrays or contact/product catalogues are loaded into the response. Billing's organisation resolver callback should accept this minimal organisation shape; existing full organisation/bulk contracts remain unchanged.
- `GET /api/v1/billing-lookups/contacts?q=text&page=1&pageSize=25&role=customer`. q trimmed maximum80 characters, page positive integer at most1000000, pageSize1–100/default25. Optional role is customer/supplier/both/other; customer/supplier include both. Result `{rows:[{public_id,name,role,active}],total,page,pageSize}`. Active, non-deleted records only; name substring/public-code search is performed in SQL after trusted tenant scope. Stable order name ASC,public_id ASC. Unknown sort/query fields rejected400. Existing master/contact:read permission.
- `GET /api/v1/billing-lookups/products?q=text&page=1&pageSize=25`. Same bounded query/response envelope; rows are `{public_id,name,unitName,active}`. Active, non-deleted products and trusted tenant-bound unit references. Existing master/product:read permission.
- `GET /api/v1/billing-lookups/contacts/:publicId` and `/products/:publicId`. Exact eight-character public IDs; no query overrides. Return the same lightweight row for an active tenant-owned record; foreign/inactive/deleted/missing rows return404. These selected-ID reads let an edit form retain its selected label even when it is outside the current search page. Missing permissions403; invalid IDs/query400.

Client additions: `getBillingBootstrap(selection)`, `searchBillingContacts({q?,page?,pageSize?,role?})`, `searchBillingProducts({q?,page?,pageSize?})`, `getBillingContact(publicId)`, `getBillingProduct(publicId)`. Existing full-record getContact/getProduct remain available for write-time validation. Billing must retain its own actor company/year policy before exposing bootstrap or lookup responses. No context or credential is cached across requests. Tenant authority never comes from search/query/header data.

Adjacent bounded setup check: `GET /api/v1/billing-setup-status`, `core.getBillingSetupStatus()` returns `{organisationReady:boolean,references:{units:boolean,currencies:boolean,taxes:boolean}}`, with no catalogue arrays or query overrides. This replaces Billing's four organisation/unit/currency/tax reads. Each reference owner performs a tenant/lifecycle-scoped active-existence query. Exact existing permission semantics remain: unit/currency/tax reads are always required; getOrganisationContext retains default-company permission and conditionally requires company/year reads only after an active default exists. Missing defaults return organisationReady:false; inactive referenced company/year retains existing conflict/error behavior. Billing computes its old ready/setup-required/unavailable presentation; Core adds no Billing state machine or currency policy.

The SQL must filter tenant and lifecycle before count/page, return exact filtered total, and never load the complete catalogue to slice it in JavaScript. No migration is planned; existing tenant/name constraints/indexes and measured query plans are checked before proposing an index. Billing/UI own bounded async lookup controls, cancellation and selected-label recovery; no arbitrary catalogue truncation or global auth caching.
